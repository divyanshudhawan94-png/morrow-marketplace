# Morrow marketplace

An early-stage multi-vendor marketplace foundation. It includes a customer storefront, account authentication, seller business verification and onboarding, draft product management, and a public catalog API/UI. Customer carts and orders are persisted in DynamoDB. A development-only checkout records orders with payment marked **Not configured** and atomically checks/decrements stock; it never charges a customer. Production payment, shipping, delivery, and refund providers are not configured.

## Architecture

- `apps/web`: Next.js App Router for the customer experience and, later, role-gated seller/admin surfaces.
- `apps/api`: Fastify service for server-side authentication and business operations.
- `packages/`: reserved for shared domain and validation packages when those contracts are implemented.
- **Primary database: Amazon DynamoDB.** A single table uses string partition/sort keys (`PK`, `SK`) for user profiles, unique email identities, sessions, seller stores, products, store product projections, SKU reservations, and audit events. Conditional transactions protect email uniqueness, store applications/approval, product writes, and per-store SKU uniqueness. Sessions have a seven-day lifetime, are stored by SHA-256 token hash, and are checked for expiry in the API. Enable DynamoDB TTL on `ttl` for cleanup; expiry checks do not depend on TTL deletion timing.
- Catalog indexes: `GSI1` lists active products by creation time; `GSI2` lists active products by category and creation time; `GSI3` lists active products by category and price; `GSI4` queues draft products for moderation; `GSI5` queues pending store applications; `GSI6` indexes sparse catalog-search token and trigram documents. Search queries use matching GSI6 partitions and fetch current product records before returning results, so archived products are excluded without walking the full catalog for each query. Search documents are separate DynamoDB items and do not rewrite product records.
- **Product media:** Sellers upload 3–5 JPEG, PNG, or WebP images per new listing (up to 5 MB each) through authenticated API endpoints. The API checks actual image contents and size, normalizes to WebP, and stores production objects in Cloudflare R2 using server-only credentials. Image order is stored with the product; the first image is its primary image. Existing single-image listings remain supported. For the guarded local workflow only, normalized images are written outside public directories and served from an exact localhost route; no R2 billing is needed. Production public HTTPS hosts remain controlled by `PRODUCT_IMAGE_HOSTS`. Sellers can save drafts, and products appear in the catalog only after super-admin moderation.
- **Seller verification:** Business details (including PAN and GSTIN where registered) are encrypted with AES-256-GCM before persistence. Identity documents use a separate private AWS S3 bucket and authenticated API downloads; they are never placed in the public product-media bucket. Format checks are not authenticity checks. Manual review is enabled; authorized government verification APIs are **NOT CONFIGURED**.
- A single web application with separated route groups avoids three separately deployed frontends until independent scaling or release needs justify that operational cost.

## Local development

Requirements: Node.js 20.9+ and npm.

```sh
npm install
Copy-Item .env.example .env
docker compose -f infrastructure/docker/compose.yaml up -d
npm run db:local:setup
npm run db:catalog-search:backfill
npm run dev
```

The web app runs on `http://localhost:3000`; the API runs on `http://localhost:4000` and its health endpoint is `/health`. The local DynamoDB container persists data in a Docker volume. The example configuration names the dedicated `marketplace-workflow-test` table; never use a production AWS endpoint for this workflow.

### Seller image uploads (Cloudflare R2)

For local development with `NODE_ENV=development`, `DYNAMODB_TABLE=marketplace-local`, and the localhost API, web, and DynamoDB Local settings shown above, the API automatically falls back to private local filesystem image storage when all five R2 settings are empty. Normalized WebP images are stored under the Git-ignored `.local-workflow-data/product-images/`, outside the public web directory, and served through the API's UUID-validated local image route. The API binds to loopback while this fallback is active. This fallback is unavailable in production; production uploads require R2 configuration and fail closed otherwise. Partial or invalid R2 configuration is reported rather than silently replaced by local storage.

For Cloudflare R2 uploads, create an R2 bucket and an R2 API token scoped to that bucket with object read/write access. Configure a public HTTPS URL for the bucket using an operator-controlled R2 custom domain (recommended) or another approved public delivery domain. Uploads are sent to the API; R2 credentials are never sent to the browser. No browser-to-R2 CORS configuration is needed.

Copy the five `R2_*` variable names from `.env.example` into the ignored root `.env` and fill them using values from your Cloudflare account. Set `R2_PUBLIC_BASE_URL` to the public HTTPS base URL (without query strings or credentials), and set `PRODUCT_IMAGE_HOSTS` to its hostname only, without the scheme or a path. For example, for a base URL `https://images.your-domain.example`, the allowlist value is `images.your-domain.example`. The API refuses partial R2 configuration or a public hostname missing from the allowlist; Next.js also uses that allowlist to configure remote images. Restart the API and web development servers after changing these settings. Never put R2 credentials in `NEXT_PUBLIC_*` variables or commit them.

To test with real images, sign in with an approved seller account, open `/seller`, choose 3–5 real JPEG, PNG, or WebP product photos (maximum 5 MB each), add descriptive alt text, arrange the images, and select the primary image. The seller form shows previews and upload progress and reports upload failures; drafts remain private until an authorized super-admin reviews and approves them. Confirm the saved gallery in the seller listing and, after approval, in `/catalog`; the primary image is used in listings, cart, checkout, and order history. The automated API tests use isolated in-memory storage and generated test image bytes; they do not create products in a configured database or contact Cloudflare. Live R2 connectivity requires your own bucket, public hostname, and secret configuration and is not exercised by local automated tests.

### Seller business verification (KYC)

Apply for a store from `/account`, then use the seller space link to complete `/seller` verification. The form requires legal and trade names, business type, PAN, business address, state, city, PIN code, a business-proof document, and consent. PAN is collected for each business type; the label clarifies whose PAN applies. A seller declares either that their business is GST-registered (GSTIN and certificate required) or that registration is not legally required. GST is not mandatory for every seller.

The API validates formats and actual JPEG/PNG/PDF signatures, stores PAN/GSTIN and business fields encrypted in DynamoDB, and stores documents privately. Only a Super Admin can fetch the review details/documents and mark a submission approved, request corrections, or reject it. Feedback is visible to the seller; corrected or rejected applications can be resubmitted. Verification approval and store approval are separate Super Admin decisions. The seller role is granted only after both, and seller-only routes and product publication are backend-gated on both approvals. This is a manual review workflow: no PAN/GSTIN is sent to a government API, and no status indicates government verification.

Before enabling submissions, configure `KYC_DOCUMENT_BUCKET` to a dedicated AWS S3 bucket that has S3 Block Public Access enabled, bucket-owner-enforced object ownership, no public website/access policy, and default encryption. Give the API runtime identity least-privilege `s3:PutObject`, `s3:GetObject`, and `s3:DeleteObject` permissions for this bucket only. The adapter does not set public ACLs and serves files only from authenticated Super Admin endpoints, but the bucket's public-access protections must be configured and verified by the operator. Set `KYC_DATA_ENCRYPTION_KEY` to a dedicated 32-byte key represented as 64 hexadecimal characters; keep it in local secret storage or a deployment secret manager, never commit it or reuse the product-image credentials. Back up and protect this key: losing it makes encrypted verification data unreadable, and key rotation requires a planned re-encryption migration. Set `AWS_REGION` for that bucket. These settings are deliberately separate from Cloudflare R2 and `PRODUCT_IMAGE_HOSTS`. Define and enforce a business/legal retention and deletion schedule for verification records and documents before production use.

Without private KYC storage and an encryption key, document submissions are disabled rather than stored insecurely. In local workflow mode, the API uses private filesystem storage and `LOCAL_KYC_TEST_KEY`; neither the private AWS bucket nor KYC encryption setting is used. API tests use injected in-memory private storage and test-only values; they do not contact AWS or create real seller data.

Customer return requests require a reason and may include up to five JPEG/PNG damage photos (5 MB each). Photos are normalized and stored in the same private document storage, never the public product-media bucket; authenticated customer and owning-seller routes control access, while Super Admin can view returns for monitoring only. The owning seller can accept the request or reject it with a reason within 24 hours. If the seller does not decide by the deadline, the system automatically accepts the return and records the system decision. Returns do not automatically issue refunds; refund processing remains separate.

For local KYC testing against existing accounts in `marketplace-local`, use the separate `LOCAL_KYC_STORAGE=true` mode. Keep `LOCAL_WORKFLOW_TESTING=false`; do not run the full seller-to-order workflow against this table. This mode is restricted to development, the `marketplace-local` table, a loopback DynamoDB Local endpoint, and the localhost web/API origins. It requires a dedicated 32-byte hexadecimal `LOCAL_KYC_TEST_KEY` and rejects AWS KYC bucket/encryption settings. The API binds to loopback and stores documents under the Git-ignored `.local-workflow-data/kyc-documents/` directory, outside the web public directory. Use only synthetic business details and generated files marked “LOCAL TEST ONLY — NOT A LEGAL DOCUMENT”; never submit real identity data. Protect the local machine and preserve the test key: losing it prevents decryption of the test verification records.

### Guarded local seller-to-order workflow

This workflow is explicitly for local development. It is not a payment, delivery, refund, or government verification integration. Keep `R2_*`, `KYC_DOCUMENT_BUCKET`, and `KYC_DATA_ENCRYPTION_KEY` empty for the local-only path. Local KYC documents and product image files are stored under the ignored root `.local-workflow-data/` directory, outside `apps/web/public`; private KYC downloads remain behind authenticated Super Admin routes. Filesystem permissions follow the host OS; protect access to your local machine and do not place real identity documents in this test store.

Customer mobile login is available only when the API detects local development (`NODE_ENV=development`, the localhost web/API origins, port 4000, and a loopback DynamoDB Local endpoint using `marketplace-local` or `marketplace-workflow-test`). Request a code at `/login`; the API prints a randomly generated six-digit OTP to its own terminal, never to the browser or API response. Codes expire after five minutes, permit at most five incorrect attempts, and can be requested once per mobile number per minute. OTPs are HMAC-protected in DynamoDB and the signing key is generated in API process memory, so restart the API and request a new code if one is outstanding. No SMS provider is configured. The API refuses to enable terminal OTP login in production; configure a real SMS provider before implementing production mobile login.

1. Copy `.env.example` to `.env` if needed. Keep `DYNAMODB_TABLE=marketplace-workflow-test`, `DYNAMODB_ENDPOINT=http://localhost:8000`, `PORT=4000`, `WEB_ORIGIN=http://localhost:3000`, and `NEXT_PUBLIC_API_URL=http://localhost:4000`. Do not point the workflow at an AWS endpoint or a shared/production table.
2. Start DynamoDB Local with the compose command above, then run `npm run db:local:setup`. This creates the dedicated test table and catalog indexes. It does not seed users or products.
3. Set `LOCAL_WORKFLOW_TESTING=true`. Generate a random test-only key locally (for example, `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`) and put its 64 hexadecimal characters in `LOCAL_KYC_TEST_KEY`. Do not reuse `KYC_DATA_ENCRYPTION_KEY`. The API refuses to start local workflow mode unless the table, loopback endpoint, localhost URLs, development environment, and test key all match. In this mode the API binds to `127.0.0.1`; R2 and private AWS S3 adapters are not used.
4. Bootstrap a local Super Admin using the existing `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` settings and `npm run db:bootstrap-admin`. Use a unique local password and remove the bootstrap values from `.env` after the one-time setup. Then run `npm run dev`.
5. In the browser, register a local seller/customer account, apply for a store, and submit verification using clearly synthetic test-only fields and a generated image/PDF marked “LOCAL TEST ONLY — NOT A LEGAL DOCUMENT.” Use `NOT_REQUIRED` for GST in this test unless you have an actual legal reason otherwise; never enter a real PAN/GSTIN or upload identity documents. The format-checked PAN field requires a format-shaped synthetic test value (for example `ZZZZZ0000Z`); it is not verified against a government system.
6. Sign in as the Super Admin at `/admin`. Review and approve the seller verification, then approve the store through the existing queues. Sign back in as the seller at `/seller`; create 3–4 drafts with ordinary, non-sensitive product photos. Their images use local private disk storage and the exact local image endpoint. Review and approve each product as Super Admin.
7. Register/sign in as a customer. From `/catalog`, add approved products to the cart. In local development, place an order with synthetic test delivery details at `/cart`; the backend saves delivery details, order snapshots, totals, timestamps, the **Not configured** payment state, and stock decrement atomically. No card fields are requested and no payment provider is called. Customer cart and order history use the authenticated account.
8. At `/admin`, use **Mark local test delivered** on one test order. Return to `/account/orders`, submit a return reason and optional damage photos, then sign in as the owning seller to accept or reject the request. If the seller does not respond within 24 hours, the system automatically accepts it. This does not issue a refund. Store/order review actions remain protected by existing RBAC.

The local adapter stores no fake catalog products or seller accounts: create test records through the existing registration, seller application, verification, store approval, product draft, and product approval screens. Clean up the dedicated DynamoDB Local table and `.local-workflow-data/` only after confirming they contain no needed test results. Never run cleanup against another table or a production endpoint.

Use `npm run lint`, `npm run typecheck`, `npm test`, and `npm run build` for checks. `.env` is ignored by Git; do not put real secrets in source control. The API requires a configured DynamoDB table and does not fall back to volatile storage.

## Authentication and access boundaries

- `POST /auth/register` always creates a customer account; roles cannot be self-selected.
- `POST /auth/login`, `POST /auth/logout`, and `GET /auth/me` manage/read an opaque server-side session.
- Passwords use Node.js scrypt with per-password random salts. Raw passwords and session tokens are never persisted.
- Session cookies are HttpOnly, SameSite=Lax, path-scoped, and Secure in production. Browser state-changing requests must include the configured exact `WEB_ORIGIN`; CORS allows that origin with credentials.
- `POST /seller/application` creates one pending store per account. It does not grant seller access.
- `GET/POST /seller/verification` allow the owner to submit, view, and resubmit private business verification. `GET /admin/seller-verifications/pending`, `GET /admin/seller-verifications/:storeId`, the authenticated document endpoint, and the review endpoint require `super_admin`. Reviews record the reviewer, timestamp, status, and reason in the audit trail.
- `POST /admin/stores/:storeId/approve` requires an existing `super_admin` role and an approved business verification. Approval atomically changes store status, grants seller role, and writes an audit event. A Super Admin cannot approve their own store or verification.
- `GET /seller/stores/:storeId` requires an approved seller, approved business verification, and verifies both store ownership and the account's linked store ID. Unknown and non-owned stores return the same not-found response.
- `POST /seller/products`, `GET /seller/products`, `PATCH /seller/products/:productId`, and `POST /seller/products/:productId/archive` provide seller-owned draft product management. `POST /seller/products/:productId/images` accepts image uploads only from an authenticated, approved seller for a draft/rejected product owned by that seller. Products have INR prices in paise, stock, SKU, category, attributes, and image metadata. Image hosts must be explicitly configured; drafts never appear in public catalog results.
- `GET /catalog` supports category, brand, text, price range, sorting, and cursor pagination. `GET /catalog/:productId` exposes active products only. The homepage and catalog pages use these endpoints for approved listings, render configured media-host images, and never substitute unrelated images. Next.js loads shared environment configuration from the monorepo root.
- `GET /admin/stores/pending`, `GET /admin/products/pending`, and the admin approve/reject endpoints are restricted to `super_admin`. Product approval requires at least one submitted image and records that the human reviewer completed an image review; rejection reasons and decisions are audited. `/admin` provides the review queue UI.
- `/seller` provides the seller's listing workspace, including editing rejected listings and resubmitting them for moderation. `/catalog` supports public browsing; `/catalog/:productId` shows active listing details.
- There is deliberately no public super-admin registration or promotion endpoint. Admin identity provisioning is a pending controlled operational procedure; do not grant the role through ordinary account registration.
- Login/registration throttles currently use an in-process store. Production multi-instance deployment needs a shared rate-limit store (for example Redis) before launch.
- The browser session setup assumes the web and API are deployed on the same site (for example, separate subdomains); cross-site deployments need a deliberate cookie/CSRF design.

### AWS table setup

Create the DynamoDB table with partition key `PK` (String), sort key `SK` (String), and on-demand billing. Add the `GSI1` (`GSI1PK`, `GSI1SK`), `GSI2` (`GSI2PK`, `GSI2SK`), `GSI3` (`GSI3PK`, `GSI3SK`), `GSI4` (`GSI4PK`, `GSI4SK`), `GSI5` (`GSI5PK`, `GSI5SK`), and `GSI6` (`GSI6PK`, `GSI6SK`) global secondary indexes, all String keys with `ALL` projection. Enable TTL using attribute `ttl`. The local setup command creates or adds these indexes and only permits a loopback endpoint. Before using search on an existing table, wait for GSI6 to become active and run `npm run db:catalog-search:backfill`; the script adds dedicated search-document items for existing active products and leaves product records unchanged. For a non-local table, set `CATALOG_SEARCH_BACKFILL_CONFIRM` to the exact `DYNAMODB_TABLE` value before running the backfill. In production, leave `DYNAMODB_ENDPOINT` unset and use an IAM task role with least-privilege access to the configured table. Keep `WEB_ORIGIN`, table name, trusted image hosts, and AWS configuration in deployment settings/secrets.

### Initial super-admin bootstrap

Provision the DynamoDB table/indexes and IAM access first. Set `BOOTSTRAP_ADMIN_EMAIL` and a strong `BOOTSTRAP_ADMIN_PASSWORD` in a trusted one-time environment, then run `npm run db:bootstrap-admin`. A conditional transaction permits only one initial bootstrap per table and creates an audit-lock record; the script accepts a custom DynamoDB endpoint only on loopback. Remove the password from the environment immediately afterward. Additional admin provisioning still requires a controlled operator workflow and must never be exposed as public registration.

## Implementation plan

1. Establish this workspace and the public experience. **Done for this initial slice.**
2. Define domain contracts, persistence/access patterns, authentication, authorization, and seller tenant isolation. **Authentication and initial seller ownership checks implemented; commerce-domain models and production admin provisioning remain.**
3. Add verified catalog ingestion/R2 media uploads, dedicated search, cart, checkout, and concurrency-safe stock handling. **Seller drafts, admin moderation, R2-backed image uploads, indexed catalog search, authenticated cart/order persistence, and development-only checkout with concurrency-safe stock decrement are implemented; real payment processing remains.**
4. Add provider interfaces and auditable order, payment, delivery, return, and refund workflows.
5. Build role-protected customer, seller, and super-admin workflows with focused integration tests. **Customer cart, development-only order placement, order history with persisted order statuses, Super Admin order-status management, seller draft catalog, and admin onboarding/product moderation slices are implemented; real payment processing and most dashboard features remain.**
6. Add operational security, monitoring, performance tests, and deployment infrastructure after core access patterns stabilize.

Real payment processing and logistics, R2 credentials, and production deployment are not configured. Local development checkout stores unpaid orders with payment status `NOT_CONFIGURED`; production checkout remains unavailable until a payment provider is integrated. Authentication, seller, catalog, and moderation web routes are wired to the API, but broader account features remain. No capacity or production-readiness claim is made.
